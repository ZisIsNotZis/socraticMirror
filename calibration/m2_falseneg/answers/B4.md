## 判断

NaN 的直接原因不是 FP16 本身，而是这条交叉熵路径**没有做 max 减法（log-sum-exp 技巧）**。该行 logits 最大 100，`exp(100) ≈ 2.69e43`，而 FP16 最大可表示值是 65504（`exp` 自变量超过 ≈11.09 就溢出）。于是 softmax 里 `exp(100) → inf`，出现 `inf/inf = NaN`，或 `log(0) = -inf` 再被 one-hot 的 0 乘出 `0·(-inf) = NaN`。

关键点：即便升到 FP32，`exp(100)` 同样超过 FP32 上限（`exp(88.7) ≈ 3.4e38`），也会溢出。所以 FP32 参考能得到 1.313，说明它**做了减 max**，而不是靠 FP32 的精度硬扛。FP16 只是把"爆点"从 logit≈88.7 提前到 ≈11.1。

## 机制（用这行数字验证）

- 该行：`z_max = 100`，`z_label = 99`（次大），其余 ≤ 0，V = 131072。
- 减 max 后：`[0, -1, ≤ -100, …]`
- `exp(0) = 1`，`exp(-1) = 0.36788`，`exp(≤ -100) ≈ 3.7e-44 → 0`（FP16 下溢，但下溢到 0 无害）
- `Σ exp = 1.36788`，`log(1.36788) = 0.31326`
- `loss = -(z_label - m) + logsum = -(-1) + 0.31326 = 1.31326 ≈ 1.313` ✓（标签是次大项，所以是 1 + 0.313）

完全对上参考值，说明只要做对减 max，FP16 也能算对这个数。

## 具体做法

**方案 A（首选，只升 loss 路径，不动全模型）**

```python
logits = lm_head_output            # [512, 128K] FP16，有限
loss = F.cross_entropy(logits.float(), labels)   # 内部自动减 max，稳定
```

`F.cross_entropy` 内部的 `log_softmax` 会先减行内最大值再 `exp`，稳定。升 FP32 只针对这 67M 个 logits 的临时张量，不涉及模型权重。

**方案 B（保持 FP16、省内存，手写稳定版）**

```python
m      = logits.max(dim=-1, keepdim=True).values   # FP16，100 精确可表示
z      = logits - m                                 # 全部 ≤ 0
logsum = z.exp().sum(-1).log()                      # exp(-1)=0.368，exp(-100)→0 无害
loss   = -(z.gather(-1, labels[:, None]).squeeze(-1) - logsum).mean()
```

**注意运算顺序**：一定要写成 `-(z_label - m) + logsum`，不要写成 `-z_label + (m + logsum)`。当 `m` 很大（如 100）时，FP16 在 100 附近的间隔是 0.0625，`m + logsum` 会先吞掉 0.313 的小量造成约 5% 的损失，而先算 `z_label - m = -1` 是精确的。

**方案 C（排查你现在的实现）**：如果现在用的是手写 `softmax` + `log`、或自定义 fused kernel，直接换掉，改用 PyTorch 的 fused `F.cross_entropy`。PyTorch 的 `log_softmax/cross_entropy` 本身带减 max，理论上 FP16 也不会 NaN——所以能 NaN 说明当前路径不是这套稳定实现，或有一个没减 max 的自定义 kernel。

**补充（非本条必需）**：logits 跑到 100 说明 lm_head 输出量级偏大，接近 FP16 安全域。若经常出现，可考虑 logits 缩放（如 `/sqrt(d_model)`）或 lm_head 输出用 FP32；但有了减 max，CE 对 logits 绝对大小是鲁棒的，这只是上游稳定性问题。

## 验证

1. **单行复现**：合成 `[100, 99, 0, …, 0]`（128K 维）和真实那一行，分别跑旧路径（应 NaN）和新路径（应 1.313）。
2. **数值断言**：`assert torch.isfinite(loss)` 且 `abs(loss.item() - 1.313) < 1e-2`（FP32 路径可到 1e-4）。
3. **梯度检查**：CE 对 logits 的梯度 = `softmax - onehot`，有界；检查 `loss.backward()` 后 logits 梯度 `torch.isfinite`，确认无 NaN 反向传播。
4. **训练守卫**：在循环里加 `if not torch.isfinite(loss): 记录 logits.max/mean 并 raise`，把 NaN 在源头抓住。
5. **集成验证**：用修好的 head 跑该 step，loss ≈ 1.313，后续几步无 NaN、权重梯度有限。

## 代价

- **方案 A**：临时 FP32 logits 张量 = `512 × 131072 × 4B = 256 MB`，loss 算完即释放；lm_head 的 matmul 仍是 FP16，计算开销可忽略（67M 元素相对 7B 前反向是零头）。若显存紧张，用 chunked/online logsumexp：两遍遍历 logits，只存标量 `m` 和 `s`，内存≈0，代价是多扫一遍 logits。
- **方案 B**：零额外内存，本行精度足够（约 1e-2），但 logits 再大时安全域比 FP32 窄，长期不如 FP32 head 稳。
- 两者都不动模型主体，满足"不能全模型 FP32"的约束。
