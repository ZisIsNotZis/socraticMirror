## 先量化，再下判断

100M 参数、float32 → 梯度量 = 100M × 4B = **400MB**。

两卡 N=2 的 ring allreduce，每卡发送量 = 2(N−1)/N × M = **1.0 × 400MB = 400MB**。10GB/s 单向 → **40ms** 通信。

实测 60ms = 20ms 计算 + 40ms 通信，正好对上。结论：**通信是计算的 2 倍，瓶颈是通信，不是计算**。所以"串行"这个标签其实不是主要问题——主要问题是 400MB 在 10GB/s 下的 40ms 硬成本。

## 先动哪一处

**先动「bucket 化 + 通信与计算重叠」，两者是一件事**：bucket 化只是让重叠可实施的机制。具体就是 PyTorch DDP（NCCL backend）默认做的那套——把参数切成若干个 bucket（默认 25MB，这里 400MB≈16 个 bucket），backward 每把一个 bucket 的梯度算完，就在独立 CUDA stream 上异步发起该 bucket 的 allreduce，同时 backward 继续往下算。

效果：步进时间从 `20+40=60ms` 变成 `max(20, 40)≈40ms`，**1.5× 吞吐，且逐 bit 损失不变**——这是唯一一个零风险、零精度代价的杠杆。

**放弃的是 lossy 梯度压缩（量化/稀疏化/TopK/PowerSGD）。** 因为它改的是优化器实际看到的梯度，训练轨迹和最终均值损失都会漂移，直接违反"全局 batch 64 的均值损失不能改"这条约束。所以它不能作为第一动，甚至在本约束下根本不能动。

## 代价

1. **显存**：bucket 化要一份梯度的暂存/聚合缓冲，梯度内存近似翻倍（这里是 400MB 级额外开销）。
2. **工程复杂度**：需要独立 stream + 事件依赖；一旦有隐式同步点，重叠会被静默打回串行。
3. **不减少字节**：重叠只是"藏"计算，不碰通信地板。它的天花板就是 40ms——**通信仍占满整步**。

这里有个必须说破的事实：在"损失逐 bit 不变 + 网络 10GB/s + 全局 batch 64"三重约束下，每卡必须把自身 400MB 梯度完整发出去一次（信息论下界），所以 **40ms/步就是无损地板**。重叠只能摸到地板，永远打不穿。

## 什么条件下会失效

1. **目标 <40ms/步**：重叠到地板后无路可走。要再快只能减少字节 → 只能 lossy 压缩 → 违反损失约束。**这是一个不可调和的三角矛盾**，此时方案直接失败。
2. **梯度分布极不均衡**：如果 400MB 集中在极少数超大层（巨型 embedding / 单个超大 matmul），那一层算完瞬间蹦出一大坨梯度，无法被切碎，backward 结束前无梯可发 → 重叠退化成串行，回到 60ms。
3. **bucket 尺寸失当**：太多太小 → NCCL 启动延迟主导、有效带宽暴跌；太大 → 重叠粒度太粗、可藏的计算太少。
4. **有隐式同步点**：优化器 step 跑在默认流、`loss.item()`、日志打印等，都会让"异步"实际变同步，overlap 静默失效——这是实践中最常见的翻车点。
5. **有效带宽 <10GB/s 或非全双工**：若 10GB/s 只是标称峰值，实际走共享 PCIe / CPU 中转 / 有争用，40ms 会被放大，重叠能藏的量不变但地板抬高。
6. **显存不够**：放不下 bucket 缓冲 → 开不了这个方案。
7. **对"损失不变"的解读放松**：如果允许"统计等价"而非"逐 bit 相同"，那重叠就不是最优第一动——压缩（如 8-bit + error feedback，或 PowerSGD）能把 400MB 砍到几十 MB、把步进压到 ~20ms（3×），但代价是梯度统计量漂移、最终损失有风险。此时"只做重叠"这个方案仍正确，但**不是最优**。

**一句话总结**：先动 bucketed 异步重叠，把 60ms 压到 40ms 的地板；放弃 lossy 压缩；方案在"必须无损、且要求快过 40ms/步"或"存在单一超大层/隐式同步/有效带宽不达标"时失效。
